# Обмен с 1С через OData

> Last reviewed: 2026-10-21

## Решение

Владелец, 2026-10-20: HTTP-сервиса `/hs/…` у 1С не будет, будет только стандартный OData
(`/<база>/odata/standard.odata`). Заказы ЛК **пишет в 1С сам**: создаёт `Document_ЗаказКлиента`.

## Как перестраиваемся

Контракт `shared/onec/schemas.ts` остаётся внутренним языком ЛК. Меняется только транспорт:
вместо `OnecClient` над `/hs/…` появляется клиент OData, который собирает те же формы ответа
из объектов 1С. Синхронизации, кэш в SQLite, страницы и мок не трогаем. Мок по-прежнему отвечает
по контракту, поэтому тесты не зависят от конфигурации 1С.

| Метод контракта | Объекты OData |
|---|---|
| каталог, группы | `Catalog_Номенклатура`, `Catalog_ВидыНоменклатуры` |
| картинки | `Catalog_НоменклатураПрисоединенныеФайлы` |
| цены | `InformationRegister_ЦеныНоменклатуры25`, `Catalog_ВидыЦен` |
| остатки | `AccumulationRegister_ТоварыНаСкладах`, `Catalog_Склады` |
| клиенты | `Catalog_Партнеры`, `Catalog_Контрагенты`, `Catalog_СоглашенияСКлиентами`, `Catalog_ДоговорыКонтрагентов`, `Catalog_СегментыПартнеров` |
| регион доставки | `Catalog_ЗоныДоставки`, `Catalog_БизнесРегионы` (#46) |
| рейсы | `Document_ЗаданиеНаПеревозку` (выпал из публикации), `Document_ЗаказКлиента` — номер и клиент заказа рейса |
| заказ и статусы | `Document_ЗаказКлиента` (запись и чтение) |

График доставки остаётся в Excel до решения #45.

## Разведка 2026-10-20: что нашли

`$metadata` — 5421 тип. Все 16 наборов первого круга опубликованы и читаются под `odata.user`.

### Главное

- **Даты изменения у объектов нет.** Курсора `changedSince` в OData не будет. Есть `DataVersion`
  (меняется при каждой записи объекта): ЛК читает полный список нужных полей (`$select`) и
  пересчитывает только строки, у которых `DataVersion` изменился. Для документов (заказы, рейсы)
  — отбор по `Date` за окно в N дней.
- **Удаление** — `DeletionMark: true` (в контракте `deleted`).
- **Ссылки** — поля `<Имя>_Key` (GUID). Названия связанных объектов в строку не приходят: их
  справочники читаем отдельно и держим в базе ЛК.
- **Кто клиент** — `Catalog_Партнеры` с `Клиент: true`. Юрлицо — `Catalog_Контрагенты`
  (`Партнер_Key`), условия — `Catalog_СоглашенияСКлиентами`.

### Заказ из ЛК

Поля `Document_ЗаказКлиента`, которые заполняет ЛК: `Date`, `Партнер_Key`, `Контрагент_Key`,
`Соглашение_Key`, `Договор_Key`, `Организация_Key`, `Склад_Key`, `Валюта_Key` (из соглашения),
`ХозяйственнаяОперация`, `ЦенаВключаетНДС`, `ДатаОтгрузки`, `ЗонаДоставки_Key`, `АдресДоставки`,
`Комментарий`, `НомерПоДаннымКлиента` = номер заявки ЛК. Строки `Товары`: `Номенклатура_Key`,
`Количество`, `КоличествоУпаковок` (= количеству: упаковки ЛК пока не продаёт, `Упаковка_Key` не
передаётся), `ВидЦены_Key`, `Цена`, `Сумма`, `СтавкаНДС_Key`, `Склад_Key`, `ДатаОтгрузки`.

Повтор без дубля: перед записью — `$filter=НомерПоДаннымКлиента eq 'ЛК-<ID сделки>'`. Нашли — берём его. Сделано — раздел «ЛК на OData», «Заказы».

### 502 на прогоне цен (2026-10-21)

Опрос результата вернул 502 — процесс ЛК не отвечал. Вероятная причина — память: контейнер
ограничен 512 МБ, а запасной путь читал наборы записей регистра цен по 200 документов за раз, и
каждый документ установки цен несёт все свои строки. В режиме образца стенд теперь берёт по 2
документа и не больше 3 страниц. Проверить, был ли контейнер убит по памяти, — `make restarts`
(`OOMKilled`, число перезапусков и последние строки лога).

### Цены: ответ 1С и прогон (2026-10-21)

Программист 1С: цены продажи — в `InformationRegister_ЦеныНоменклатуры` (вся история изменений,
более 4 млн записей — история цен, ответ программиста 1С 2026-10-21); `ЦеныНоменклатуры25` пуст; срез последних регистр отдаёт. Прогон стенда:
`…/SliceLast()` у самого регистра — HTTP 400 «Обнаружены лишние сегменты в запросе к контейнеру
сущностей»; набор записей — 40 с на 2 документа. Поэтому:
- читаем только `ЦеныНоменклатуры`, срез — у `InformationRegister_ЦеныНоменклатуры_RecordType/SliceLast()`
  (регистр подчинён регистратору), прежний путь — запасной;
- срез страницами по 5000 строк (`$top`/`$skip`): весь ответ разом кладёт процесс по памяти;
- наборы записей больше не читаем: история цен целиком нам не нужна и слишком медленна.

## Клиент OData: каталог (сделано)

`server/services/onecOdata.ts`, класс `ODataClient`:
- `catalog({ page, pageSize })` отдаёт `CatalogPage` контракта и проверяет его схемой;
- товары — `Catalog_Номенклатура` с `IsFolder eq false`, страницы через `$top`/`$skip` по `Ref_Key`;
- разделы — группы номенклатуры (`IsFolder eq true`) плюс раздел «Без группы» для товаров вне групп;
- `changedAt` — момент чтения, курсора нет: каждый прогон полный;
- запасные значения, пока справочники не опубликованы: единица «шт», бренд пустой, кратность и
  минимум 1, свойств и аналогов нет. Хэш картинки — по ссылке на файл.

Проверка — стенд, режим «OData 1С — каталог»: справочники, первые 50 товаров через тот же клиент,
схема контракта, образец десяти товаров. Тесты — `tests/onecOdata.test.ts`.

Прогон на тестовой базе 2026-10-20: единиц 10523, марок 836, разделов 1161; из первых 50 товаров
48 с артикулом и 20 с картинкой — каталог проходит схему контракта.

## Клиент OData: цены и остатки (сделано)

- `prices({ priceTypes? })` — действующие цены из `InformationRegister_ЦеныНоменклатуры25`: сначала
  срез последних (`/SliceLast()`); если 1С его не отдаёт — все записи регистра и последняя активная
  по дате (медленнее, стенд пишет, каким путём прочитано). Цены характеристик и упаковок пропускаем.
  Валюта — `Catalog_Валюты` (буквенный код из наименования или по числовому), без валюты строка не
  отдаётся. НДС — `Catalog_Номенклатура.СтавкаНДС_Key` → `Catalog_СтавкиНДС` (поле `Ставка` или «20%»
  в наименовании). Даты 1С — по Минску (`+03:00`).
- `stock()` — `AccumulationRegister_ТоварыНаСкладах/Balance(Dimensions='Номенклатура,Склад')`,
  свободно = `ВНаличии − КОтгрузке`, не меньше нуля; название склада — `Catalog_Склады`.
- Прогон 2026-10-20: остатки — 20750 строк по 37 складам; среди складов автомобили, офисы и
  «собственные нужды». Решение владельца 2026-10-21: клиенту — только «Основной склад». Список задаёт
  `ONEC_STOCK_WAREHOUSES` (наименования через запятую), пусто — «Основной склад».
- Прайс в том же прогоне — 0 строк: среза последних нет, запасной путь `_RecordType` пуст. Теперь
  пробуем по очереди срез с `$select`, срез без `$select` и наборы записей регистра
  (`InformationRegister_X` — регистр подчинён регистратору, строки лежат в `RecordSet`); стенд
  показывает, что не сработало и сколько записей отброшено по каждой причине.
- Оба метода отдают всё целиком и проверяют каждую строку схемой контракта.

Проверка — стенд, режим «OData 1С — цены и остатки»: способ чтения прайса, число строк по видам цен
и складам, валюты, образцы с названиями товаров. Выбранный режим стенд помнит.

В синхронизацию ЛК клиент включается окружением `ONEC_MODE=odata` — раздел ниже.

## ЛК на OData: каталог, картинки, цены, остатки (2026-10-21)

Включается окружением: `ONEC_MODE=odata`, `ONEC_URL` — адрес публикации OData, вход —
`ONEC_LOGIN`/`ONEC_PASSWORD` (стандартная публикация 1С принимает Basic; `ONEC_TOKEN` тоже передаётся,
если публикация за прокси с Bearer). `ONEC_PRICE_TYPES` — виды цен по наименованию через запятую (пусто — все),
`ONEC_STOCK_WAREHOUSES` — склады (пусто — «Основной склад»). Код: `server/services/onecOdataSource.ts`
(`OdataOnec` в роли `useOnec()`), `server/utils/odataSnapshot.ts` (страницы снимка, моменты по версиям),
`server/utils/odataVersions.ts` (таблица `odata_version`).

- **Каталог.** Разделы — виды номенклатуры (`Catalog_ВидыНоменклатуры`, решение владельца §2.2),
  товар — по `ВидНоменклатуры_Key`. Номенклатура читается целиком страницами по 5000; момент
  изменения товара — первый прогон, в котором ЛК увидел его версию (`DataVersion`). Неизменные
  товары дальше не приходят, кроме строк на границе курсора (граница включена, §1.5).
- **Картинки.** `Catalog_НоменклатураПрисоединенныеФайлы` по `ФайлКартинки_Key`, base64 из
  `ФайлХранилище_Base64Data`, тип — по расширению (jpg, png, webp).
- **Цены.** Срез `ЦеныНоменклатуры_RecordType/SliceLast()` страницами по 5000, только заданные виды
  цен; момент — первый прогон, в котором ЛК увидел новую версию строки (цена, валюта, НДС,
  `Period`), а не сам `Period`: цену, внесённую задним числом, курсор по `Period` пропустил бы. Цена 0 уходит как удалённая: в ЛК «нет цены». Новый вид цен в
  `ONEC_PRICE_TYPES` подтянет старые цены только после сброса курсора потока `prices`.
- **Остатки.** `ТоварыНаСкладах/Balance` по складам из `ONEC_STOCK_WAREHOUSES` — снимком: строки,
  которых нет в снимке, ЛК удаляет (товар ушёл со склада). Удаляет только после удачного непустого
  снимка не меньше половины того, что уже лежит в ЛК: пустой или резко усохший снимок больше похож
  на сбой 1С, чем на пустой склад, — остаются вчерашние остатки и предупреждение в логе.
- **Не сделано по OData:** график доставки — в 1С его нет (Excel, #45). В режиме `odata` поток
  отвечает ошибкой 501, расписание его пропускает, «Состояние системы» и оповещения его не ждут;
  мок не подставляется. Режима «часть потоков по OData, часть по HTTP-сервису» нет.
  `ONEC_MOCK=true` перекрывает `ONEC_MODE=odata` (в логе предупреждение).
- **Рейсы** (`server/services/onecOdataTrips.ts`) — **написаны по типовой ERP и стендом не
  проверены**: `Document_ЗаданиеНаПеревозку` выпал из публикации, поэтому поток **выключен, пока не
  задано `ONEC_ODATA_TRIPS=true`** (без флага `trips()` отвечает 501 для любого вызывающего).
  Включить, когда документ вернут, после прогона стенда: имена полей, значения статуса, время.
  - Только проведённые задания с плановым началом от 7 дней назад до 30 вперёд; без плановой даты
    рейс пропускается, рейс, ломающий контракт, — тоже (со счётчиком в логе `[onec:odata] trips`).
    Не пришли табличные части вовсе — ошибка прогона (значит, 1С их не отдаёт по `$select`).
  - Даты `ДатаВремяРейсаПланС/ПланПо/ФактС/ФактПо` — время Минска; статус: `Формируется` —
    «формируется», `КПогрузке` — «к погрузке», `Отправлено` — «отправлен», `Закрыто` — «закрыт»,
    незнакомый — «формируется» (клиенту ничего не обещает).
  - Зоны — `Маршрут.Зона_Key`, это те же зоны доставки, что `region` клиента (#46) — проверить.
  - Заказы — `Распоряжения` типа «заказ клиента» (перемещения и прочее пропускаются); номер и клиент
    — из `Document_ЗаказКлиента` пачками по 40; не найденный заказ в рейс не попадает (счётчик в
    логе). Кривые GUID в фильтр не идут.
  - Рейс заказа клиенту (`tripGuid` в статусах заказов) — из этих же рейсов: позднейший по плановому
    началу, удалённые не назначаются. Рейсы не прочитались — прогон статусов заказов тоже падает
    (иначе ЛК стёр бы у заказов уже известные рейсы). Момент изменения рейса — по версии документа и
    его заказов. Распроведённый или вышедший из окна рейс просто перестаёт приходить: в ЛК остаётся
    последнее известное, а витрина рейсов показывает только предстоящие.
- **Заказы** (`server/services/onecOdataOrders.ts`) пишутся в 1С, поэтому запись **выключена, пока
  не задано `ONEC_ODATA_ORDERS=true`** — для любого вызывающего, включая MCP `onec_create_order`.
  `sync:orders` при этом работает: досылает заявки в сделки Б24 и пишет в них отчёт, а подтверждённые
  заявки ждут включения; статусы из 1С не читаются. Тестовый заказ стенда работает и без
  переменной: он ничего не пишет.
  - **Документ пишется непроведённым** (ревью PR #65): OData минует формы и согласование 1С, а
    проведение сразу резервирует товар. Согласует и проводит заказ менеджер в 1С; ЛК видит статус
    «новый», пока документ не проведён. Резерв по OData не узнать: в ответе ЛК резерв = количеству,
    а цена — та, что ушла в заказ; поэтому комментарий о расхождениях цены и резерва в сделку в этом
    режиме не приходит — их видно в 1С при проведении.
  - Заявка → `Document_ЗаказКлиента` (поля — раздел «Заказ из ЛК» выше): соглашение — только этого
    клиента и действующее, контрагент — первый неудалённый, склад — из соглашения, иначе первый по
    справочнику складов, чьё наименование есть в `ONEC_STOCK_WAREHOUSES`; адрес — строка контактной
    информации с тем же GUID, что ЛК отдал клиенту; НДС — ставка номенклатуры. Чего-то нет — отказ
    без записи.
  - Повтор без дубля: номер заявки — `ЛК-<ID сделки>` (номер — до 37 безопасных символов, маркер — до
    40, иначе отказ: он обязан влезть в `НомерПоДаннымКлиента` без обрезки — длину поля проверить) в `НомерПоДаннымКлиента`; нашли документ —
    возвращаем самый ранний по номеру (помеченный на удаление — как «отменён», второй не пишем),
    чужого клиента — 409. Гонка двух процессов на одной заявке не
    закрыта: писатель один (`sync:orders`, ручной запуск с ним не пересекается).
  - Тестовый заказ (`test: true`, §1.7) проверяет все ссылки, существующий документ не ищет и ничего
    не пишет; стенд «клиенты и соглашения» делает такой заказ для первого клиента с соглашением и
    адресом.
  - Статусы — заказы с маркером `ЛК-` за 90 дней: помечен на удаление — «отменён», не проведён —
    «новый», `КОбеспечению` — «подтверждён», `КОтгрузке` — «собран», `Закрыт` — «отгружен» (закрытый
    отказ так не отличить); «доставлен» и рейс заказа — после рейсов по OData. Значения перечислений
    взяты из типовой конфигурации — **проверить на тестовой базе**.
  - **До включения:** только на тестовой базе 1С (`ONEC_URL` — её публикация) и после решения #46: у клиента с несколькими соглашениями заказ уходит по самому позднему. Тестовый заказ на стенде; один настоящий заказ на тестовой базе — сверить с
    заказом, созданным в 1С руками (реквизиты, проведение менеджером); значения `Статус`.
  - **Откат:** заказы ЛК находятся в 1С отбором `НомерПоДаннымКлиента` начинается с `ЛК-`; лишние —
    пометить на удаление в 1С (ЛК покажет их «отменёнными»).
- **Клиенты и соглашения** (`server/services/onecOdataClients.ts`). Поток клиентов уходит в
  компании Б24 (`sync:companies`), поэтому по OData он **выключен, пока не задано
  `ONEC_ODATA_CLIENTS=true`**: включать после проверки стендом, тестовую базу 1С — только с
  тестовым порталом. Стенд работает и без переменной.
  - Читаются партнёры с `Клиент = true` (помеченные на удаление приходят с `deleted: true`),
    контрагенты, соглашения, договоры, контактная информация, зоны доставки, валюты и сегменты партнёров — **всё
    обязательно**: не прочиталось — прогон падает, в ЛК ничего не меняется. Иначе пустой набор
    соглашений, зон или сегментов затёр бы договоры, регионы и запрет отгрузки у всех клиентов разом.
  - УНП — первый непустой `ИНН` неудалённых контрагентов партнёра (по `Ref_Key`);
  - зона доставки — `ЗонаДоставки_Key` → `Catalog_ЗоныДоставки` (поле `region`, #46); нет — `null`,
    дату доставки не обещаем;
  - запрет отгрузки — партнёр в `Catalog_СегментыПартнеров_ПартнерыПоСегменту` неудалённого
    сегмента с `ЗапретОтгрузки`;
  - адреса — строки `Catalog_Партнеры_КонтактнаяИнформация` с `Тип = Адрес`, без дублей; `address`
    и `city` — из первой по `LineNumber`. Пока все виды адресов (какой — «доставки», покажет стенд).
    GUID адреса — из партнёра, вида, города и текста: правка текста в 1С даёт новый адрес;
  - соглашение — из действующих (`Статус = Действует`, не удалено, сегодня по Минску в датах
    действия) только с видом цен и известной валютой; из них самое позднее по началу действия, затем
    по дате, затем по ссылке. Выбор из нескольких в корзине — #46. Подходящих нет — договора нет,
    цен клиент не видит. Номер — соглашения, иначе договора; дата — соглашения, начала действия или
    договора, иначе `2000-01-01`; лимит — `ДопустимаяСуммаЗадолженности` договора.
  - **Пока не заполняется:** e-mail менеджера (компания Б24 остаётся без ответственного по менеджеру
    1С, docs/plan.md), отсрочка (табличная часть «Этапы графика оплаты»), долг (регистр расчётов не
    опубликован) — пусто и 0; в профиле клиента долг 0 значит «нет данных».
  - Момент изменения — по хешу всего, что видит ЛК: изменилось соглашение, адрес или зона —
    клиент приходит заново.
  - Стенд: режим «OData 1С — клиенты и соглашения» — счётчики, статусы соглашений, сколько
    действующих у клиента, виды цен и адресов, зоны, образец 10 клиентов. Отчёт копируют в чат:
    адресов, e-mail и телефонов нет, УНП — «есть/нет», название — только у организаций с формой и названием в кавычках (у ИП это ФИО, прочее скрыто).
- **Снимок и кэш.** OData не умеет «изменённое с момента», поэтому каждый прогон читает объект
  целиком; страницы прогона берутся из снимка в памяти процесса (живёт 2 минуты после загрузки,
  ошибка не кэшируется).
- **Нагрузка на 1С — замерить до боевой базы.** Каталог раз в час, цены раз в 15 минут и остатки
  раз в 5 минут читаются целиком (цены — регистр более 4 млн записей; срез по нужным видам цен меньше, но 1С строит его по всему регистру — нагрузка на 1С не замерена). Ответ OData
  ограничен 64 МБ (считается в байтах при чтении потока), картинка — 8 МБ; не больше 500 страниц
  по 5000 строк на объект, запрос — до 120 с. Версии цен лежат в `odata_version` и пишутся одной
  транзакцией — на первом прогоне это сотни тысяч строк: замерить время и память (контейнер 512 МБ).
- **Пропавшее из 1С.** Остатки, которых нет в снимке, ЛК удаляет; товары и цены, исчезнувшие из
  выдачи OData (а не помеченные на удаление или с нулевой ценой), остаются в ЛК — дочистка следующим
  шагом.
- **Ограничение: заменённая картинка.** Имя файла картинки строится из её идентификатора, а не из
  содержимого: если в 1С заменить файл под тем же идентификатором, ЛК его не перекачает.

## Шаги

1. **Разведка полей.** Стенд `/api/onec-test`, режим «OData 1С — разведка полей»: читает
   `$metadata` и по одной строке ключа каждого набора. Показывает, что опубликовано, что читается,
   и имена с типами полей. Значений не читает. Кнопка «Скопировать поля для разработчика» даёт текст
   для разработчика.
2. По полям — сопоставление «поле 1С → поле контракта» в этом документе.
3. ✅ Клиент OData: каталог, картинки, цены, остатки, клиенты и соглашения (раздел выше).
4. ✅ Запись заказа и статусы (раздел «ЛК на OData», «Заказы»).
5. Рейсы — написаны, ждут публикации `Document_ЗаданиеНаПеревозку` и проверки стендом. Дальше — несколько соглашений в
   корзине (#46) и график доставки (#45).

## Риски

- **Заказ мимо проверок 1С.** OData пишет документ напрямую, обработчики формы не работают.
  Обязательные реквизиты (соглашение, склад, валюта, хозяйственная операция) заполняет ЛК.
  Проверять на тестовой базе.
- **Права.** Пользователю OData нужна запись в `Document_ЗаказКлиента` и чтение только перечисленного.
  Сейчас в публикации есть зарплата и персональные данные (`ФизическиеЛица`, `Сотрудники`,
  `НачислениеЗарплаты`), публикацию нужно сузить до таблицы выше.
- **Нагрузка.** OData отдаёт сырые таблицы. Читаем с `$select` и страницами, как и раньше, по одному
  запросу за раз (`onecGuard`).
